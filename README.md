# MemoryLifecycle

Консольный проект на .NET 10 для исследования сборки мусора и управления временем жизни объектов. Проект выполнен в рамках контрольной точки по дисциплине "Язык программирования C#" (КТ №40-43, раздел "Время жизни объектов").

## Цель проекта

Сформировать практические навыки анализа поведения сборщика мусора .NET, научиться осознанно управлять временем жизни объектов и оформить результаты исследования в виде воспроизводимого проекта на GitHub.

## Задачи

1. Изучить поколения сборки мусора (Gen0, Gen1, Gen2), большие и пришпиленные кучи (LOH, POH), регионы памяти и механизм DATAS.
2. Научиться измерять поведение GC через встроенные API .NET (`GC.CollectionCount`, `GC.GetTotalAllocatedBytes`, `GC.GetGCMemoryInfo`) и правильно объяснять полученные значения.
3. Сравнить режимы Workstation GC и Server GC и разобраться, зачем нужна фоновая сборка.
4. Написать классы с финализатором, интерфейсом `IDisposable` и проверить работу конструкции `using`.
5. Освоить полный паттерн Dispose и асинхронное освобождение ресурсов через `IAsyncDisposable`.
6. Оформить результаты в виде проекта GitHub с README, папкой docs и понятной историей коммитов.
7. Подготовить ответы на контрольные вопросы по изученному материалу.


Запуск:

```bash

dotnet run --project src/MemoryLifecycle -c Release -- gc-modes
dotnet run --project src/MemoryLifecycle -c Release -- resources
dotnet run --project src/MemoryLifecycle -c Release -- dispose
```

## Результаты

### КТ №40. Поколения и давление на кучу

Условия запуска: Windows, .NET 10, Workstation GC, конфигурация Release.

Сценарии из `PressureScenarios.cs`:

- **Мелкие объекты** - 100 000 массивов `byte[100]`, каждый сразу становится мусором;
- **Крупные объекты** - 10 массивов `byte[100_000]`, больше порога 85 000 байт, поэтому попадают в LOH;
- **Удерживаемые объекты** - 20 000 массивов `byte[512]` в статическом списке, они остаются достижимыми;
- **Принудительный Gen2** - вызов `GC.Collect(2, GCCollectionMode.Forced, blocking: true)`.

| Сценарий | Время, мс | Gen0 | Gen1 | Gen2 | Alloc, МБ | Heap Δ, МБ |
|---|---:|---:|---:|---:|---:|---:|
| Мелкие объекты | 8,56 | 2 | 0 | 0 | 12,21 | 0,05 |
| Крупные объекты | 0,04 | 0 | 0 | 0 | 0,95 | 0,00 |
| Удерживаемые объекты | 7,96 | 1 | 0 | 0 | 10,72 | 6,65 |
| Принудительный Gen2 | 0,76 | 1 | 1 | 1 | 0,00 | 4,93 |

Всего аллоцировано с начала работы: 23,90 МБ. В статическом списке удерживается 20 000 объектов.

Состояние кучи до и после экспериментов (`GC.GetGCMemoryInfo`):

| Показатель | До | После |
|---|---:|---:|
| HeapSizeBytes | 0,00 МБ | 11,64 МБ |
| TotalCommittedBytes | 0,00 МБ | 18,09 МБ |
| MemoryLoadBytes | 0,00 МБ | 9974,74 МБ |
| PauseTimePercentage | 0,00 % | 4,03 % |
| Режим GC | Workstation | Workstation |

Как читать таблицу:

- у мелких объектов 12,21 МБ аллокаций дали всего две сборки Gen0, а куча выросла всего на 0,05 МБ, потому что все объекты уже были мусором;
- у крупных объектов сборок нет совсем, а Heap Δ равен нулю: массивы легли в LOH, но сборки не было, поэтому `GetGCMemoryInfo` ещё показывает старые данные;
- у удерживаемых объектов после сборки Gen0 куча выросла на 6,65 МБ, это выжившие объекты из статического списка;
- принудительный Gen2 увеличивает сразу все три счётчика, потому что сборка старшего поколения всегда включает младшие, и после неё куча выросла ещё на 4,93 МБ: стала видна оставшаяся часть удерживаемых объектов;
- до экспериментов все значения `GetGCMemoryInfo` равны нулю, потому что ни одной сборки ещё не было, а после них размер кучи 11,64 МБ, это в основном 20 000 удерживаемых массивов (около 10,7 МБ).

**Выводы:**

1. Короткоживущие мелкие объекты нагружают в основном Gen0. Они умирают молодыми, поэтому сборки Gen0 дешёвые, а Gen2 почти не растёт.
2. Крупные объекты (от 85 000 байт) сразу попадают в LOH и обходят Gen0. LOH логически относится к Gen2, но счётчик Gen2 увеличивается только когда реально происходит сборка, а не в момент выделения памяти.
3. Долгоживущие объекты, которые держит статический список, переживают сборки и переходят в Gen2. Их вклад в `HeapSizeBytes` становится виден только после следующей сборки, потому что `GC.GetGCMemoryInfo` возвращает данные о последней сборке.

### КТ №41. Режимы сборки мусора

Режим переключался через свойство `ServerGarbageCollection` в файле `MemoryLifecycle.csproj` (`true` или `false`). Тест: 4 потока, каждый создаёт 300 000 объектов. Каждый режим запускался в трёх условиях: без нагрузки, с открытым браузером, с браузером и воспроизведением 4K видео.

| Показатель | WS, без нагрузки | WS, браузер | WS, браузер + 4K | Server, без нагрузки | Server, браузер | Server, браузер + 4K |
|---|---|---|---|---|---|---|
| Server GC | False | False | False | True | True | True |
| Latency mode | Interactive | Interactive | Interactive | Interactive | Interactive | Interactive |
| Потоков / объектов на поток | 4 / 300 000 | 4 / 300 000 | 4 / 300 000 | 4 / 300 000 | 4 / 300 000 | 4 / 300 000 |
| Принудительный Gen2 (до / после) | 0,97 / 0,65 мс | 1,27 / 0,66 мс | 0,85 / 0,66 мс | 1,56 / 0,63 мс | 1,98 / 0,61 мс | 1,25 / 1,30 мс |
| Время параллельной аллокации | **30,60 мс** | **31,81 мс** | **48,83 мс** | **47,31 мс** | **51,23 мс** | **105,47 мс** |
| Gen0 / Gen1 / Gen2 | 24 / 1 / 0 | 24 / 1 / 0 | 24 / 1 / 0 | 27 / 5 / 4 | 32 / 5 / 4 | 33 / 4 / 3 |
| Аллоцировано | 146,49 МБ | 146,49 МБ | 146,49 МБ | 146,49 МБ | 146,49 МБ | 146,49 МБ |
| Контрольная сумма | 152985664 | 152985664 | 152985664 | 152985664 | 152985664 | 152985664 |

Контрольная сумма и объём аллокаций одинаковые во всех запусках, значит программа делала одну и ту же работу и сравнение честное.

**Выводы:**

1. Workstation GC оказался быстрее во всех сценариях: 30,60-48,83 мс против 47,31-105,47 мс у Server GC.
2. Скорее всего, это связано с накладными расходами Server GC: он создаёт отдельную кучу и поток сборки на каждое логическое ядро, и их нужно координировать. На коротком тесте с небольшим объёмом аллокаций (около 146 МБ) эти расходы больше, чем выигрыш от параллельной сборки.
3. Server GC сделал больше сборок (27-33 сборки Gen0 против стабильных 24 у Workstation) и при этом запускал ещё сборки Gen1 и Gen2. Это не обязательно плохо: у Server GC другие бюджеты поколений и другая логика запуска сборок.
4. Воспроизведение 4K видео замедлило оба режима, но Server GC сильнее всего (до 105,47 мс). Думаю, это потому что его потоки сборки конкурируют за процессор с декодированием видео, а Server GC рассчитывает на то, что все ядра свободны.
5. Выводы сделаны по одному короткому запуску на каждое условие, поэтому они не окончательные. Для точного сравнения нужно делать несколько прогонов, отбрасывать первый (прогрев JIT) и считать среднее или медиану.

### КТ №42. Финализатор и IDisposable

Демонстрации находятся в `ResourceDemos.cs`: работа финализатора, освобождение через `using`, сценарий с забытым `Dispose()` и запись в лог-файл через класс `LogFile`.

**Выводы:**

1. `IDisposable` управляется программистом: ресурс освобождается сразу при выходе из блока `using`, момент освобождения известен заранее.
2. Финализатор вызывает сборщик мусора, когда сам решит, обычно когда не хватает памяти. Предсказать этот момент нельзя.
3. Если забыть вызвать `Dispose()`, ресурс освободится только в финализаторе, то есть с задержкой. Для файла это значит, что он может оставаться заблокированным.
4. Поэтому `IDisposable` это основной способ освобождения любых ресурсов, а финализатор нужен только как страховка для неуправляемых ресурсов. Кроме того, финализатор замедляет сборку мусора.

### КТ №43. Паттерн Dispose и IAsyncDisposable

Классы `DatabaseConnection` и `FileBuffer` реализуют и `IDisposable`, и `IAsyncDisposable`. В `Program.cs` проверяется два варианта:

- `DatabaseConnection` открывается через `using` и `await using`, выполняются запросы `SELECT * FROM Students` и `SELECT * FROM Topics`, потом вызываются `GC.Collect()` и `GC.WaitForPendingFinalizers()`;
- `FileBuffer` открывается через `using` и `await using`, в него записываются данные `{1, 2, 3, 4}` и `{5, 6, 7}`.

**Выводы:**

1. Метод `protected virtual Dispose(bool disposing)` разделяет две задачи. При явном вызове (`disposing = true`) освобождаются управляемые объекты (`List` и `MemoryStream`). На любом пути, в том числе из финализатора, закрываются неуправляемые дескрипторы (в проекте это имитация).
2. Асинхронное освобождение идёт через `DisposeAsyncCore()`, обёрнутый в `try/finally`, поэтому нативные ресурсы закрываются даже если при асинхронной очистке произошла ошибка.
3. Флаг `disposed` и обнуление ссылок защищают от повторной очистки, поэтому повторный вызов `Dispose()` ничего не ломает.
4. После `Dispose()` и `DisposeAsync()` вызывается `GC.SuppressFinalize(this)`, поэтому после принудительной сборки финализатор уже не срабатывает. Это видно по выводу программы: сообщения из финализатора нет.
5. Проверка через `using`, `await using` и `GC.Collect()` показала, что память и ресурсы освобождаются корректно.

## Общие выводы

1. Основная нагрузка на GC создаётся короткоживущими объектами в Gen0, и это нормально, так как сборка Gen0 самая дешёвая.
2. Крупные объекты попадают в LOH, а долгоживущие уходят в Gen2. Чем больше объектов доживает до Gen2, тем дороже обходятся полные сборки.
3. Server GC не всегда быстрее. На коротких задачах и на машине, где процессор занят другими программами, Workstation GC может работать лучше.
4. Сравнивать режимы GC по одному запуску нельзя, нужны повторные измерения.
5. `Dispose` освобождает ресурс детерминированно, а финализатор нет. Финализатор нужен только как страховка.
6. Полный паттерн Dispose разделяет управляемые и неуправляемые ресурсы, защищает от повторного вызова и вместе с `GC.SuppressFinalize` убирает лишнюю работу финализатора.
7. `IAsyncDisposable` и `await using` нужны, когда при закрытии ресурса есть асинхронные операции, например сброс буфера или закрытие соединения.

## Ответы на контрольные вопросы

### КТ №40. GC в .NET 10: поколения, регионы памяти (DATAS)

**1. Почему новые объекты размещаются в Gen0? В чём суть гипотезы о смертности молодых объектов?**

Гипотеза о поколениях говорит, что большинство объектов живут очень недолго: создали временную строку или массив, поработали с ним и он уже не нужен. Поэтому все новые объекты кладутся в Gen0, и сборщик чаще всего проверяет только эту маленькую область. Так как почти всё в Gen0 уже мусор, сборка проходит быстро и освобождает много памяти. В проекте это видно на сценарии "Мелкие объекты": 100 000 массивов `byte[100]` дают только сборки Gen0, а Gen2 не растёт.

**2. Как объект попадает в Gen1 и Gen2? Почему сборка Gen2 дороже сборки Gen0?**

Если объект пережил сборку Gen0 (на него ещё есть ссылка), он переводится в Gen1. Если он пережил и сборку Gen1, то попадает в Gen2. Gen1 работает как буфер между короткоживущими и долгоживущими объектами. Сборка Gen2 это полная сборка: проверяются все поколения и LOH, а там обычно много живых объектов, которые надо обойти и, возможно, переместить. Поэтому она занимает больше времени. В проекте объекты из статического списка `LongLived` в сценарии "Удерживаемые объекты" как раз уходят в Gen2.

**3. Что такое LOH? При каком размере объект туда попадает и почему LOH по умолчанию не уплотняется?**

LOH (Large Object Heap) это куча для больших объектов. Туда попадают объекты размером 85 000 байт и больше, чаще всего большие массивы. LOH логически относится к Gen2 и собирается только при полной сборке. Уплотнение по умолчанию не делается, потому что копировать большие блоки памяти очень дорого. Минус в том, что LOH может фрагментироваться. Уплотнить его можно вручную через `GCSettings.LargeObjectHeapCompactionMode`. В проекте массивы `byte[100_000]` в сценарии "Крупные объекты" попадают именно в LOH.

**4. Что такое POH и какую проблему он решает?**

POH (Pinned Object Heap) появился в .NET 5. Это отдельная куча для пришпиленных (pinned) объектов, то есть таких, которые GC не имеет права перемещать, например буферы, переданные в нативный код. Раньше такие объекты лежали в обычных поколениях и мешали уплотнению, создавая дыры в памяти. Теперь их можно сразу выделить в POH через `GC.AllocateArray<T>(length, pinned: true)`, и они не мешают сборке остальной кучи.

**5. Что изменилось с переходом на регионы памяти в .NET 7 и новее? Почему регионы называют деталью реализации?**

Раньше каждое поколение жило в больших непрерывных сегментах. С .NET 7 управляемая куча делится на небольшие регионы, и каждый регион принадлежит какому-то поколению. Регион можно легко передать другому поколению или вернуть системе, поэтому память используется гибче и освобождается быстрее. Это называют деталью реализации, потому что для программиста ничего не меняется: API, поколения и правила работы остаются теми же, код переписывать не нужно.

**6. Что такое DATAS? Как он влияет на потребление памяти в контейнерах?**

DATAS (Dynamic Adaptation To Application Sizes) это механизм, который подстраивает размер кучи и количество куч Server GC под реальную нагрузку приложения. В .NET 10 он включён по умолчанию для Server GC. Без него Server GC сразу создаёт кучу на каждое ядро и резервирует много памяти. С DATAS приложение начинает с одной кучи и добавляет новые только при росте нагрузки. В контейнерах с ограничением памяти это сильно снижает потребление и позволяет запускать больше экземпляров на одном сервере.

**7. Что возвращают GC.CollectionCount, GC.GetTotalAllocatedBytes и GC.GetGCMemoryInfo? Почему HeapSizeBytes может быть равен нулю?**

- `GC.CollectionCount(n)` возвращает, сколько раз была сборка поколения n с момента запуска процесса. В проекте считается разница до и после сценария.
- `GC.GetTotalAllocatedBytes(precise: true)` возвращает, сколько байт всего было выделено за время работы процесса, включая уже освобождённое.
- `GC.GetGCMemoryInfo()` возвращает информацию о последней сборке: размер кучи, фрагментацию, нагрузку на память и другое.

`HeapSizeBytes` может быть равен нулю, потому что эти данные заполняются только после сборки. Если ни одной сборки ещё не было, информации о куче просто нет. Поэтому в моём выводе вклад удерживаемых объектов виден только после следующей сборки.

### КТ №41. Параллельная и фоновая сборка мусора

**8. Сравните Workstation GC и Server GC по количеству куч, потокам сборки, целям и потреблению памяти.**

| | Workstation GC | Server GC |
|---|---|---|
| Количество куч | одна | по одной на каждое логическое ядро (с DATAS меньше) |
| Потоки сборки | сборка идёт в потоке, который её вызвал | отдельный поток сборки на каждую кучу |
| Цель | быстрый отклик, короткие паузы | максимальная пропускная способность |
| Память | меньше | больше, так как куч и бюджетов больше |

Workstation подходит для десктопных и консольных приложений, Server для серверов и веб-сервисов с большой нагрузкой.

**9. Что такое Background GC? Какие фазы сборки всё равно останавливают управляемые потоки?**

Background GC это фоновая сборка Gen2. Пока она идёт в отдельном потоке, программа продолжает работать и может выделять память, а сборки Gen0 и Gen1 (эфемерные) выполняются параллельно с ней. Но полностью без пауз не обходится: потоки останавливаются в начале сборки (поиск корней и подготовка маркировки) и в конце (завершение маркировки). Также останавливают потоки сами эфемерные сборки и любые блокирующие сборки, например вызванные с `blocking: true`.

**10. Почему GC.Collect(2, GCCollectionMode.Forced, blocking: true) не рекомендуется применять в производственном коде?**

Этот вызов запускает полную блокирующую сборку: все управляемые потоки останавливаются, пока GC проходит по всей куче. Это дорого и даёт заметные паузы. Кроме того, сборщик сам лучше знает, когда собирать, а ручной вызов ломает его статистику и бюджеты поколений. Объекты, которые были бы нужны чуть позже, могут лишний раз переехать в Gen2. В проекте я использую этот вызов только для эксперимента, чтобы измерить паузу Gen2.

**11. Как включить Server GC и как проверить, что режим действительно изменился?**

Включить можно несколькими способами:

- в .csproj: `<ServerGarbageCollection>true</ServerGarbageCollection>` (так делал я);
- в `runtimeconfig.json`: `"System.GC.Server": true`;
- через переменную окружения `DOTNET_gcServer=1`.

Проверить режим можно через `GCSettings.IsServerGC`. В моей таблице есть строка "Server GC", которая как раз выводит это значение (False или True). Также можно смотреть на `GCSettings.LatencyMode`.

**12. Почему Server GC может показывать больше сборок Gen0? Является ли это признаком деградации?**

У Server GC несколько куч, и у каждой свой бюджет Gen0. Сборка может запускаться, когда заканчивается бюджет на любой из куч, плюс на работу влияет DATAS, который сначала держит мало куч и маленькие бюджеты. Поэтому сборок может быть больше. Это не обязательно деградация: каждая сборка может быть короче и идёт параллельно. Оценивать надо по общему времени и паузам, а не только по количеству. У меня Server GC сделал 27-33 сборки Gen0 против 24, и в этом тесте он действительно был медленнее, но на долгой серверной нагрузке картина может быть другой.

**13. Почему одного короткого запуска недостаточно для сравнения режимов GC?**

Один запуск сильно зависит от случайных факторов: прогрев JIT в первом запуске, другие программы на компьютере, частота процессора, кэш. Мой эксперимент это хорошо показывает: просто включённое 4K видео замедлило Server GC с 47 до 105 мс. Чтобы сравнение было честным, нужно делать несколько прогонов, отбрасывать первый, считать среднее или медиану и запускать в одинаковых условиях. Для этого есть BenchmarkDotNet.

### КТ №42. Финализируемые объекты. IDisposable. using

**14. Когда вызывается финализатор? Почему его вызов считается недетерминированным?**

Финализатор вызывается после того, как GC обнаружил, что объект недостижим, и поставил его в очередь финализации. Потом отдельный поток финализации вызывает метод `~ClassName()`. Это недетерминированно, потому что мы не знаем, когда произойдёт сборка: это зависит от выделения памяти и решений GC. Также не гарантирован порядок вызова финализаторов, а при завершении процесса они могут вообще не вызваться. В `RunFinalizerDemo` я вызывал `GC.Collect()` и `GC.WaitForPendingFinalizers()` специально, чтобы увидеть сообщение финализатора.

**15. Почему финализируемые объекты живут дольше обычных?**

Когда создаётся объект с финализатором, GC записывает его в специальный список. При сборке такой объект не удаляется сразу, а переносится в очередь финализации, и он снова становится достижимым. Из-за этого он переживает сборку и переходит в следующее поколение. Память освобождается только на следующей сборке после того, как финализатор отработал. В итоге объект живёт минимум на одну сборку дольше, и вместе с ним живут все объекты, на которые он ссылается.

**16. Что гарантирует IDisposable.Dispose() и чем он отличается от финализатора?**

`Dispose()` гарантирует детерминированное освобождение: ресурс закрывается ровно в тот момент, когда мы вызвали метод (или вышли из блока `using`). Вызывает его программист, в нужном потоке, и можно освобождать как управляемые, так и неуправляемые ресурсы. Финализатор вызывает GC в неизвестный момент в потоке финализации, и в нём нельзя трогать другие управляемые объекты, потому что они уже могут быть собраны. Сам `Dispose()` память не освобождает, память всё равно освобождает GC.

**17. Как компилятор разворачивает оператор using? Что происходит при исключении внутри блока?**

Компилятор превращает `using` в `try/finally`:

```csharp
var res = new LogFile("memory-lifecycle.log");
try
{
    // тело блока
}
finally
{
    res?.Dispose();
}
```

Поскольку `Dispose()` находится в `finally`, он вызовется даже если в блоке выбросилось исключение. Ресурс закроется, а исключение пойдёт дальше по стеку.

**18. Чем using-оператор отличается от using-декларации?**

Using-оператор пишется с блоком: `using (var x = ...) { ... }`, и `Dispose()` вызывается при выходе из этого блока. Using-декларация появилась в C# 8: `using var x = ...;` без скобок и блока. `Dispose()` вызывается в конце области видимости, обычно в конце метода. Декларация короче и уменьшает вложенность, но ресурс держится дольше. Если несколько деклараций, они освобождаются в обратном порядке.

**19. Что происходит при повторном вызове Dispose()? Как обеспечить идемпотентность?**

По правилам .NET повторный вызов `Dispose()` не должен выбрасывать исключение и не должен ещё раз освобождать ресурс. Если этого не обеспечить, можно, например, дважды закрыть один дескриптор. Идемпотентность делается через флаг:

```csharp
private bool _disposed;

protected virtual void Dispose(bool disposing)
{
    if (_disposed) return;
    // освобождение
    _disposed = true;
}
```

В моих классах `DatabaseConnection` и `FileBuffer` так и сделано, а ссылки после очистки обнуляются. Методы, которые используют ресурс после закрытия, должны бросать `ObjectDisposedException` (можно через `ObjectDisposedException.ThrowIf(_disposed, this)`).

### КТ №43. Паттерн Dispose. IAsyncDisposable (.NET 10)

**20. Зачем нужен Dispose(bool disposing)? Какие ресурсы освобождаются при true, а какие при false?**

Этот метод собирает всю логику освобождения в одном месте, а параметр показывает, откуда его вызвали. При `true` вызов идёт из `Dispose()`, то есть явно от программиста: можно освобождать и управляемые ресурсы (у меня это `List` и `MemoryStream`), и неуправляемые. При `false` вызов идёт из финализатора: другие управляемые объекты уже могут быть собраны, поэтому трогать их нельзя, освобождаются только неуправляемые ресурсы (дескрипторы). Метод `protected virtual`, чтобы наследники могли его дополнить.

**21. Что делает GC.SuppressFinalize и почему его вызывают в Dispose() и DisposeAsync()?**

`GC.SuppressFinalize(this)` говорит сборщику, что финализатор этого объекта вызывать не надо, и убирает объект из списка финализации. Его вызывают в `Dispose()` и `DisposeAsync()`, потому что ресурсы уже освобождены и финализатор больше не нужен. В результате объект не попадает в очередь финализации, не живёт лишнюю сборку и освобождается сразу как обычный объект.

**22. Что такое IAsyncDisposable? В каких сценариях он необходим?**

`IAsyncDisposable` это интерфейс с методом `ValueTask DisposeAsync()`. Он нужен, когда при закрытии ресурса есть операции ввода-вывода, которые лучше выполнять асинхронно, чтобы не блокировать поток. Например: сброс буфера в файл или сеть, закрытие соединения с базой данных, завершение сетевого потока. В проекте `FileBuffer` при асинхронном закрытии сбрасывает данные, а `DatabaseConnection` закрывает соединение.

**23. Почему рекомендуется реализовывать оба интерфейса, IDisposable и IAsyncDisposable?**

Потому что класс могут использовать по-разному. Где-то код синхронный и вызывается `using` или `Dispose()`, а где-то асинхронный с `await using`. Если реализовать только `IAsyncDisposable`, то обычный `using` не скомпилируется, а если только `IDisposable`, то в асинхронном коде поток будет блокироваться на вводе-выводе. С двумя интерфейсами класс работает правильно в обоих случаях. В проекте я проверял оба варианта для `DatabaseConnection` и `FileBuffer`.

**24. Что делает await using? Чем он отличается от обычного using?**

`await using` разворачивается в `try/finally`, где в `finally` вызывается `await res.DisposeAsync()`. Обычный `using` вызывает синхронный `Dispose()`. Разница в том, что при `await using` освобождение не блокирует поток, и метод должен быть `async`. Также `await using` требует, чтобы тип реализовал `IAsyncDisposable`.

**25. Как производный класс должен переопределять Dispose(bool) и DisposeAsyncCore()?**

Производный класс не переопределяет сами `Dispose()` и `DisposeAsync()`, а только виртуальные методы:

```csharp
protected override void Dispose(bool disposing)
{
    if (!_disposed)
    {
        if (disposing)
        {
            // освободить свои управляемые ресурсы
        }
        // освободить свои неуправляемые ресурсы
        _disposed = true;
    }
    base.Dispose(disposing);
}

protected override async ValueTask DisposeAsyncCore()
{
    // асинхронно освободить свои ресурсы
    await base.DisposeAsyncCore();
}
```

Главное не забыть вызвать базовую версию, лучше в `finally`, иначе ресурсы базового класса не освободятся. У наследника должен быть свой флаг `_disposed`.

**26. Как доказать, что финализатор не вызвался после Dispose()?**

Нужно добавить в финализатор вывод в консоль или счётчик. Потом создать объект, вызвать `Dispose()` (или выйти из `using`), обнулить ссылку и запустить `GC.Collect()`, `GC.WaitForPendingFinalizers()` и ещё раз `GC.Collect()`. Если сообщения из финализатора нет, значит `GC.SuppressFinalize(this)` сработал. Для сравнения можно создать такой же объект без `Dispose()`, и у него сообщение появится. В моём `Program.cs` после `using` и `await using` как раз вызываются `GC.Collect()` и `GC.WaitForPendingFinalizers()`, и в выводе нет строк финализатора.

**27. Какие ошибки типичны при реализации DisposeAsync()?**

- Забыть вызвать `GC.SuppressFinalize(this)` в `DisposeAsync()`.
- Не вызвать `Dispose(false)` после `DisposeAsyncCore()`, из-за чего неуправляемые ресурсы не закрываются.
- Вызывать внутри синхронный `Dispose()` или делать `.Result` и `.Wait()`, что блокирует поток и может дать дедлок.
- Не проверять флаг `_disposed`, и тогда повторный вызов освобождает ресурс второй раз.
- Не использовать `try/finally`, из-за чего при исключении часть ресурсов не освобождается.
- Возвращать `Task` вместо `ValueTask` или делать `async void`.
- В наследнике забыть вызвать `base.DisposeAsyncCore()`.
- Использовать `using` вместо `await using`, и тогда вызывается только синхронный `Dispose()`.
